# AGENTS.md - Guidelines for AI agents

Этот файл содержит инструкции для AI-ассистентов (OpenCode, Cursor, Copilot и др.), работающих с этим репозиторием. Цель — обеспечить высокое качество, консистентность и безопасность генерируемого кода.

## 🚨 Главные правила (TL;DR)

1. **Никогда не коммитьте сломанный код.** Если правка затрагивает несколько слоёв (vdom, layout, paint, runtime) — это **один** компилируемый коммит.
2. **Всегда проверяйте `git status --short` перед `light publish`**. Публикация с "грязным" деревом приведёт к сбою и рассинхронизации версий на crates.io.
3. **Правило доказательств (UI/CLI)**: если вы меняете `layout`, `paint`, `init` или `dev`, вы **обязаны** приложить скриншот или лог успешного запуска (smoke-тест). Код без визуального подтверждения не принимается.
4. **Обновление версий**: Bump версии делается отдельным коммитом `chore(release): bump to X.Y.Z`, после чего ставится тег и только потом запускается публикация.
5. **Документация под контролем**: Перед началом работы **прочитайте** `docs/` и `README.md`, чтобы понять контекст. **Запрещено самостоятельно менять файлы документации**. Если вы меняете API или поведение — предложите правки и дождитесь явного подтверждения (см. *Documentation-First Policy*).
6. **Стоп-и-спроси при конфликте.** Если файл/функция/структура уже существует с другой семантикой — остановись, сформулируй вопрос (формат ниже), дождись решения. НЕ переписывай. НЕ создавай параллельную версию. Детали — в разделе «Правило: Стоп-и-спроси при конфликте с существующим кодом».

## Documentation-First Policy (Правило документации)

В этом проекте документация не является второстепенной. Любое изменение в коде должно быть отражено в ней, но **только с ведома пользователя**.

1. **Чтение перед правками**: Перед тем как предлагать архитектурные изменения, добавление новых элементов, фич или модификацию CLI, агент **обязан** изучить существующие документы (`docs/ARCHITECTURE.md`, `docs/COMPONENT_MODEL.md`, `docs/guide.md`), чтобы не нарушить заложенные принципы.
2. **Режим "Propose & Approve" (Предложение и Подтверждение)**:
   - Если ваши изменения в коде требуют правок в документации (добавлена функция, фича, изменился CLI), вы **не имеете права** молча изменять `.md` файлы.
   - Вы должны написать в ответе блок **"📝 Предлагаемые изменения в документации"**.
   - Указать точные файлы, разделы и желаемый текст (или показать diff).
   - Дождаться явного ответа пользователя (например, "Применяй", "Согласен").
   - Только после этого вы имеете право внести изменения в файлы `docs/` и `README.md` через инструменты редактирования.
3. **Синхронизация**: Если пользователь одобрил правки, убедитесь, что:
   - Обновлены все релевантные файлы (`README.md`, `docs/quickstart.md`, `docs/guide.md`, `docs/RELEASING.md` и т.д.).
   - Обновлено оглавление (TOC), если добавлялись новые разделы.
4. **Никаких «фантомных» фич**: Запрещено описывать в документации то, чего нет в коде, или оставлять в доках упоминания удалённых функций.

## Правило: Стоп-и-спроси при конфликте с существующим кодом

Если при выполнении ТЗ вы обнаруживаете, что файл/функция/структура
**уже существует** и имеет семантику, отличную от той, что описана в ТЗ
(или ТЗ её не описывает вовсе) — вы **обязаны** остановиться и задать
вопрос. НЕ переписывать. НЕ удалять. НЕ создавать параллельную версию
(«search_v2.rs», «new_registry.rs» и т.п.).

### Когда это правило срабатывает (триггеры)

1. Файл уже существует, но ТЗ предполагает его «создать».
   → Сначала прочитайте его. Поймите, что он делает.
2. Функция уже есть, но её сигнатура/поведение не совпадает с ТЗ.
   → Проверьте, кто её вызывает (`grep` по crate).
3. Структура данных уже определена, но в ТЗ другие поля/семантика.
   → Проверьте, где она используется (`grep`).
4. Тесты уже покрывают поведение, которое ТЗ хочет изменить.
   → Прочитайте тесты — они фиксируют контракт.
5. Есть несколько кандидатов на «место» (например, два модуля
   с похожей ролью). → Не угадывайте. Спросите.
6. ТЗ противоречит сам себе или противоречит AGENTS.md / существующей
   документации (`docs/ARCHITECTURE.md`, `docs/COMPONENT_MODEL.md`).

### Формат вопроса (обязательный)

Не пишите «найдено, что делать?». Формулируйте так:

```
## ⚠️ Конфликт: <файл или функция>

**Что есть сейчас:**
- `<путь>` — <1-2 строки описания семантики>
- Используется в: <список вызовов / модулей>
- Покрыто тестами: <да/нет, где>

**Что требует ТЗ:**
- <1-2 строки>

**Варианты:**
A. Расширить существующий (сохранить API, добавить новое).
B. Заменить (сломать обратную совместимость).
C. Создать параллельный (не рекомендуется — дублирование).
D. Другое (опишите).

**Моя рекомендация:** <A/B/C/D с обоснованием в 1 предложение>.

**Жду решения.** Ничего не меняю до ответа.
```

### Пример: реальный кейс (Этап 0 Plugin API, ноябрь 2026)

```
## ⚠️ Конфликт: crates/light-cli-core/src/registry.rs и search.rs

**Что есть сейчас:**
- `registry.rs` — bundled-таблица известных компонентов (2-3 шт.
  из `registry.toml`), работает офлайн, используется в `light check`,
  `light dev`, `light build` для auto-install. НЕ про URL.
- `search.rs` — простой `light search <query>`: HTTP через trait
  `RemoteRegistry`, фильтр по префиксу `light-fw-`, таблица
  NAME/VERSION/DESCRIPTION/URL. Без owners, без валидации,
  без interactive выбора.
- Оба покрыты тестами (4 + 3 шт.), зелёные.

**Что требует ТЗ (Этап 0):**
- Расширяемый реестр (`RegistryConfig` с URLs из `light.config.json`).
- `light search` с галкой official, `--yes`, `--json`, скачиванием
  .crate и валидацией `[package.metadata.light]`.

**Варианты:**
A. Расширить: `registry.rs` не трогать (только комментарий),
   `search.rs` дополнить новыми функциями, `fetch.rs` расширить
   trait, новые файлы `registry_config.rs`, `metadata.rs`.
   Старые тесты остаются зелёными, auto-install не ломается.
B. Переписать `search.rs` с нуля под новые требования.
C. Создать `search_v2.rs` параллельно.

**Моя рекомендация:** A. Bundled `registry.toml` и `ComponentRegistry`
понадобятся в Этапе 1 (`light check` использует и bundled-таблицу,
и remote registry). Удалять/переименовывать нельзя.

**Жду решения.**
```

### Почему это правило критично

- **Скрытая регрессия.** Если переписать `registry.rs` — сломается
  auto-install в `light dev`/`light build`. Мы узнаем это только
  на e2e у пользователя. Починка — ещё одна итерация.
- **Потеря контракта.** Тесты фиксируют поведение, которое кто-то
  (возможно, другая задача) ожидает. Удалять их без обсуждения —
  значит откатывать ранее принятые решения.
- **Дублирование.** `search_v2.rs` рядом со `search.rs` — через 3 месяца
  никто не помнит, какой используется. Один модуль = одна
  ответственность.
- **Трата времени.** Один вопрос = 1 минута. Переписывание + откат +
  повторная реализация = 2-3 часа.

### Связанные правила

- **Documentation-First Policy** (Propose & Approve) — для `.md` файлов.
- **Правило доказательств** (UI/CLI) — для layout/paint/init/dev.
- **Правило «Стоп-и-спроси»** (это) — для кода, который уже существует.

Все три правила работают по одной логике: **не угадывай — уточняй**.

## Build, Lint, and Test Commands

Используйте эти команды для проверки и валидации изменений.

```bash
# Форматирование кода (Rust)
cargo fmt --all

# Линтинг (Clippy со строгими предупреждениями)
cargo clippy --workspace --all-targets --all-features -- -D warnings

# Сборка всех целей (bin, lib, tests)
cargo build --all-targets

# Запуск всех тестов
cargo test --all-features
```

### Особенности Windows (MSVC)
На Windows из-за лимита длины командной строки (D8050) сборка крейта `ring` (через `reqwest` в CLI `light`) может падать при параллельной сборке.
Обход:
```powershell
$env:CARGO_BUILD_JOBS = "1"
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features -j 2
```

**`cargo build -p light` (debug) с фичей `network`** — `reqwest` → `ring`
превышает лимит командной строки MSVC (D8050). Обход:
- `cargo build --release -p light` (release работает);
- `cargo clippy -p light-fw-cli-core --no-default-features -- -D warnings`
  (без network — для проверки логики);
- полный clippy с network — только в CI (Linux).

## CI Workflow (.github/workflows/ci.yml)

CI состоит из 15 джобов:

- `fmt` (Linux): `cargo fmt --all -- --check`.
- `docs` (Linux): `mdbook build`.
- `clippy` (3 OS): `cargo clippy --all-targets --all-features -- -D warnings`.
- `test` (3 OS): `cargo test --all-features` + `cargo bench --no-run`.
- `build-default` (Windows): сборка примеров без `--all-features`.
- `features` (Linux, 6 вариантов): `cargo test -p light-fw --no-default-features --features "..."`.

### Обязательные правила

1. **Локальный прогон перед push** (минимум):
   ```powershell
   $env:CARGO_BUILD_JOBS = "1"
   cargo fmt --all -- --check
   cargo clippy --workspace --all-targets --no-default-features -- -D warnings
   cargo test --workspace --all-features --release -j 2 --no-fail-fast
   ```
   Если 0 failed — можно пушить. Иначе — фиксить до пуша.

2. **D8050 (Windows debug)**: `cargo build -p light` (debug) с
   фичей `network` падает. Использовать `--release` или
   `--no-default-features`. См. `docs/TODO_TESTS.md`.

3. **CARGO_BUILD_JOBS в workflow**: не ставить пустую строку
   (`''`). Использовать `'default'` или конкретное число.

4. **Features-джобы**: таргет `-p light-fw` (не `-p light` —
   фичи живут в мета-крейте).

5. **После пуша**: смотреть CI-status PR. Если красный — фиксить
   немедленно (не откладывать). Красный CI на release-ветке —
   блокер мержа.

### Что НЕ делать

- ❌ Не отключать джобы через `if: false` или `continue-on-error: true`
  ради зелёного CI.
- ❌ Не добавлять `#[ignore]` в тесты ради прохождения.
- ❌ Не мержить с красным CI.
- ❌ Не создавать push в master без PR (кроме hotfix-релизов,
  согласованных с пользователем).

## Development Workflow (Правильная последовательность)

1. **Изучение контекста**: Прочитайте `docs/ARCHITECTURE.md` и релевантные разделы `docs/guide.md` перед планированием.
2. **Планирование**: Составьте детальный план изменений.
3. **Проверка конфликтов**: Перед написанием кода пройдитесь по триггерам из «Правило: Стоп-и-спроси» — если находите существующие файлы с другой семантикой, задайте вопрос и дождитесь решения.
4. **Реализация**: Пишите идиоматичный Rust-код, следуя принципам минимизации аллокаций.
5. **Локальные гейты**:
   - `cargo fmt --all`
   - `cargo build --workspace --exclude light --exclude light-fw-cli-core` (если `ring` блокирует сборку).
   - `cargo clippy`
   - `cargo test`
6. **Smoke Test (для UI/CLI)**:
   - Если менялся `init`, `dev`, `layout` или `runtime`:
   - Создайте чистый проект: `light init test-smoke`
   - Запустите `light dev` в нём.
   - Убедитесь, что окно открывается, текст рендерится, DevTools запускается.
   - Сделайте скриншот.
7. **Подготовка документации (Propose & Approve)**:
   - Сформируйте список необходимых изменений в доках.
   - Выведите его пользователю.
   - **Дождитесь апрува.**
   - После апрува — внесите изменения.
8. **Коммит**: Используйте Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`). В сообщении коммита укажите, если были обновлены доки (например, `feat(devtools): ... (+ docs)`).

## Branching Strategy

### Ветки по версиям

Каждая минорная версия (0.19.0, 0.20.0, ...) разрабатывается в
отдельной ветке:

- **Имя:** `release/X.Y.0` (например, `release/0.19.0`).
- **База:** `master` в состоянии, где CI зелёный.
- **Мерж:** только после завершения **всех** этапов версии +
  CI 15/15 зелёный + docs обновлены + CHANGELOG + bump версии.

### Feature-ветки внутри версии (опционально)

Для крупных подзадач можно создавать временные ветки от
`release/X.Y.0` (например, `feat/0.19.0-plugin-api`), но они
мержатся **в release-ветку**, не в master.

### Правила PR

- **Draft PR** создаётся в первый день работы над версией
  (`release/X.Y.0 → master`).
- Push в release-ветку **автоматически обновляет PR** и
  триггерит CI.
- PR мержится **только** после полной готовности версии.
- Название PR: `Release X.Y.0: <краткое описание>`.

### Почему так

- CI `ci.yml` триггерится только на `push: master` и
  `pull_request: master`. Push в `feat/*` **не запускает CI**.
  Draft PR решает это: он виден в CI с первого дня.
- Пользователь видит "в работе" через PR, но master остаётся
  стабильным (0.18.0) до полной готовности 0.19.0.

## Pre-existing Failures: правило "чинить, а не игнорировать"

Если CI на release-ветке красный, но падения **не связаны с
изменениями ветки** (проверено через `git stash` + повторный
прогон на чистом HEAD):

1. **Не игнорировать.** Красный CI на PR блокирует мерж.
2. **Фиксить в этой же ветке.** Не откладывать "на потом" —
   отдельный коммит `test: fix pre-existing <тест>` или
   `ci: fix pre-existing <проблема>`.
3. **Документировать в `docs/TODO_TESTS.md`:**
   - Что было сломано.
   - Причина (в 1-2 предложениях).
   - Как починено (с хешем коммита).
4. **Если нельзя починить сейчас** (например, требует решения
   пользователя или внешней инфраструктуры):
   - Добавить в `TODO_TESTS.md` с явным приоритетом.
   - Если блокирует CI — обсудить с пользователем, возможно
     временно отключить в workflow с явным TODO-комментарием
     (и это тоже задокументировать).

### Как отличить pre-existing от нашего

```bash
git stash
git checkout <commit-before-our-changes>
cargo test <failing-test>  # если падает — pre-existing
git checkout <our-branch>
git stash pop
```

Если падает на чистом HEAD — pre-existing. Если проходит —
наш баг.

### Частые причины pre-existing failures

- **Hardcoded versions** (`"0.7.0"` вместо `ComponentRegistry::builtin()`).
  Фикс: читать из источника истины (registry, env!, fixtures).
- **Flaky timing** (`assert_ne!(Instant::now(), Instant::now())`).
  Фикс: добавить `sleep(1-10ms)` или заменить на монотонный счётчик.
- **Platform-specific** (Windows `.exe`, Unix без расширения).
  Фикс: `#[cfg(windows)]` / `#[cfg(not(windows))]`.
- **Network-dependent** в unit-тестах (mock должен быть).
  Фикс: mock server (wiremock), не реальная сеть.
- **God-test** (тест проверяет слишком много). Фикс: разбить или
  убрать нерелевантные assertion'ы.

## Release Workflow (Публикация)

**Категорически запрещено** публиковать крейты, если `git status --short` не пуст.

1. **Bump версий**: Обновите версии во всех `Cargo.toml` и `Cargo.lock`.
2. **CHANGELOG**: Добавьте раздел в `CHANGELOG.md` (формат Keep a Changelog).
3. **Коммит и тег**:
   ```bash
   git add -A
   git commit -m "chore(release): bump to X.Y.Z"
   git tag -a vX.Y.Z -m "Release X.Y.Z: <features>"
   git push origin master
   git push origin vX.Y.Z
   ```
4. **Публикация**:
   ```bash
   light publish --yes --skip-gates --no-verify
   ```
5. **Верификация**: Проверьте, что все крейты опубликованы:
   ```bash
   cargo search light --limit 1
   ```

**Примечание (с 0.18.0):** в воркспейсе **9 публикуемых крейтов** (включая `light-fw-devtools-web`, который публикуется как зависимость `light` bin). `light publish` подхватывает их автоматически, но перед публикацией полезно проверить `docs/RELEASING.md` — там актуальный порядок.

## Code Style Guidelines

### Форматирование
- Используйте `cargo fmt` с настройками из `.rustfmt.toml`.
- Отступы: 4 пробела. Длина строки: 100 символов.

### Именование
- **Типы**: `PascalCase` (`ClientConfig`, `ParseError`).
- **Функции и методы**: `snake_case` (`parse_input`, `is_valid`).
- **Константы**: `SCREAMING_SNAKE_CASE` (`MAX_RETRIES`).
- **Модули**: `snake_case` (`file_reader`).

### Импорты
Группируйте импорты в порядке: `std` → внешние крейты → `crate` (локальные).
```rust
use std::{collections::HashMap, time::Duration};
use serde::{Serialize, Deserialize};
use crate::{config::Config, error::AppError};
```

### Обработка ошибок
- **Библиотечный код**: используйте `thiserror`. **Не используйте `anyhow` в библиотеках**.
- **Прикладной код (binary)**: допускается `anyhow`.
- Избегайте `unwrap()` и `expect()` в production-коде. Используйте `?`.

### Типы и сериализация
- Используйте `serde` с `derive` для JSON-сериализации.
- Предпочитайте строго типизированные структуры вместо `serde_json::Value`.
- Для строковых параметров используйте `impl Into<String>`.

### Документация
- Публичные элементы должны иметь doc-комментарии (`///`).
- Примеры в doc-комментариях должны компилироваться (проверяются через `cargo test`).

## Как обновить дефолтную иконку

Иконка окна по умолчанию хранится в **сырых RGBA-байтах** (без PNG-кодека, чтобы
`light-fw-core` оставался без зависимостей от image-библиотек для дефолтной иконки):

- Файл: `crates/light-core/assets/default_icon.rgba`
- Размер: 128×128 пикселей, 4 байта на пиксель → **65 536 байт** в файле.
- Формат: `[R, G, B, A]` в порядке следования строк — ровно тот layout, который
  принимает [`winit::window::Icon::from_rgba`](https://docs.rs/winit/latest/winit/window/struct.Icon.html#method.from_rgba).
- Встраивается в бинарник через `include_bytes!` в `crates/light-core/src/window/icon.rs`.

Чтобы заменить иконку новым изображением (PNG/WebP/JPG с альфа-каналом или
сквозным фоном), сконвертируйте его в raw RGBA той же ширины/высоты:

```python
# Python + Pillow. Замените SOURCE.png на новый файл.
from PIL import Image
import os

SOURCE = "logo.png"          # исходный файл (любой формат, понимаемый Pillow)
DST    = "crates/light-core/assets/default_icon.rgba"
SIZE   = 128                 # должно совпадать с DEFAULT_ICON_SIZE в icon.rs

im = Image.open(SOURCE).convert("RGBA").resize((SIZE, SIZE), Image.LANCZOS)
data = im.tobytes("raw", "RGBA")   # [R,G,B,A] * w*h, row-major
assert len(data) == SIZE * SIZE * 4
os.makedirs(os.path.dirname(DST), exist_ok=True)
with open(DST, "wb") as f:
    f.write(data)
print(f"wrote {DST} ({len(data)} bytes = {SIZE}x{SIZE} RGBA)")
```

Если у исходника нет прозрачности (как в текущей иконке — сплошной синий квадрат),
добавьте mask со скруглёнными углами, как это делалось при генерации текущего
файла (см. git-history для скрипта с `rounded_alpha()`).

После конвертации пересоберите крейт:

```bash
cargo build -p light-fw-core
cargo test  -p light-fw-core --lib window::icon
```

Тесты в `icon.rs` проверяют: длину файла (128²·4), прозрачный угол (0,0),
непрозрачный центр (64,64) и наличие обоих типов пикселей — они не дадут
случайно закоммитить битый файл.

## Testing UI with DevTools (как агенту видеть и трогать UI)

Light предоставляет headless-инструменты для автономного тестирования UI:

1. **Запуск с сессией:** `light dev --agent` — создаёт `.light/agent-sessions/<id>/` и пишет каждый вызов `light devtools` в `actions.jsonl`.
2. **Скриншот:** `light devtools shot --path shots` → сохраняет PNG в `shots/<YYYYMMDD_HHMMSS>.png` (при указании каталога, имени без расширения или `.`; точный путь вида `out/frame.png` используется как есть). Без `--path` печатает сырой base64 в stdout — для редиректа (`light devtools shot > raw.b64`). Ошибки сервера (не запущен, unknown command) выводятся человекочитаемо и завершают команду с кодом 1.
3. **Поиск элемента:** `light devtools find --tag button --text "+1"` → `{key, tag, rect}`.
4. **Клик:** `light devtools click --key 0.0.0`.
5. **Ввод:** `light devtools type --key 0.0.1 "Hello"`.
6. **Клавиша:** `light devtools key --key 0.0.1 Enter`.
7. **Состояние:** `light devtools state` (JSON) и `light devtools tree`.
8. **Завершение:** `light devtools session stop` → генерирует `summary.md`.
9. **Центрирование заголовков:** `<h1>`–`<h5>` внутри `align-items=center` авторазмериваются (max-content) и центрируются. С версии 0.16.2 всегда (раньше получали width=0).
10. **Браузерный UI:** `light dev` поднимает Web UI на `http://127.0.0.1:9228` (флаги `--no-web`, `--web-port`). Сервер — tiny_http (без tokio), SSE каждые 500 мс. Если приложение не запущено — бейдж «Ожидание приложения…».

**Агент обязан:** после тестирования приложить `summary.md` и скриншоты из `screenshots/` к отчёту.

## Запрещённые практики

- ❌ `unwrap()` / `expect()` в production-коде без крайней необходимости.
- ❌ `panic!()` для обработки ожидаемых ошибок.
- ❌ `unsafe` без явного обоснования.
- ❌ Хардкод значений, которые могут быть параметрами.
- ❌ Игнорирование предупреждений компилятора и Clippy.
- ❌ **Публикация (`light publish`) без чистого `git status`.**
- ❌ **Правки в `layout.rs` или `runtime.rs` без визуального подтверждения (скриншота).**
- ❌ **Самостоятельное редактирование `.md` файлов без предварительного согласования с пользователем.**
- ❌ **Переписывание или удаление существующего кода при обнаружении конфликта с ТЗ** (см. «Правило: Стоп-и-спроси»).
- ❌ **Создание параллельных версий** (`*_v2.rs`, `new_*.rs`) без явного согласования.
